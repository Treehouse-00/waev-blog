The question comes up early in any evaluation: before you enroll an observer, before anything flows — what does a tool like this actually keep?

It's the right question to ask first. What doesn't enter the database can't be accessed, breached, or misused. The architecture's privacy posture isn't defined by what it promises to protect, but by what it declines to collect in the first place — so this post lists what Waev keeps, field by field.

<div class="callout">
<p><strong>TLDR:</strong> Waev stores signal metadata (SNR per link, hop count, timing), topology edges labeled by evidence class, records for infrastructure nodes including their advertised positions, and the raw frame of every packet in a publicly served archive. At ingest it drops ADVERTs from opted-out nodes and blanks companion names and keys, but keeps companion device types and coordinates in analytics rows for about 90 days.</p>

## What arrives at the ingest edge

Your mesh observer receives every LoRa packet that passes through it and publishes those records directly to Waev's own MQTT ingest, using a credential that can only send its own data — it can't read, alter, or delete anything else on the broker. What arrives at Waev's ingest edge is a stream of raw packet records: the source node's name, the path the packet traveled, signal quality readings at each hop, and a timestamp.

That stream contains more information than Waev needs. The ingest path reduces some of it before anything is written to Waev's database, and keeps the rest. One consumer receives the stream before any reduction: when an affiliated partner is connected, Waev forwards observers' raw publishes for that partner's regions to a subscribe-only feed.

## The three decisions at the gate

**First: privacy markers.** If an ADVERT's node name contains ⛔, 🛑, or 🚫, and the node isn't an enrolled observer, the packet is discarded before any database or analytics write. Nothing from that ADVERT is counted or stored. The check runs after the partner feed, when connected, has received the raw frame, and after the packet is decoded; it logs the node's public key and name when it fires; and packets that carry no name are not checked.

This is the strongest of the three checks: not "we anonymize it" or "we aggregate it," but "this ADVERT doesn't enter the database." A node that opts out does not disappear entirely: its earlier row and position stay until the 182-hour prune, a discovery response can still create a nameless node row, and name history, analytics rows, and archived frames from before the marker stay.

**Second: companion device scrub.** MeshCore personal apps — phones and tablets running as companion devices — broadcast on the same RF mesh as repeaters. Their packets reach observers just like any other node's packets. At ingest, a companion ADVERT's name and public key are blanked before analytics rows are written and before the packet reaches the live feed. The device type and any GPS coordinates are kept in analytics rows for about 90 days, along with SNR, hop count, and timing, and the raw frame is archived whole. The device counts in Network Stats as traffic, but never appears on the Live Map.

**Third: the physics gate.** Every map line carries an evidence class. Proven and Corroborated lines come from receptions that observers measured. Inferred lines are reconstructed from relayed path hashes — 1-byte to 3-byte key prefixes that nobody signs — and the default map draws them at reduced opacity. Links that fail the physics gate are classed Rejected and left off the default map. Repeater ADVERT signatures are checked and recorded, but production runs that check in observe mode, so an invalid signature doesn't stop an advert.

## What actually gets stored

What Waev keeps is wider than this post used to say:

</Figure>

- **SNR per link** — the signal-to-noise ratio as measured at each hop in the path. The number that tells you whether a link is healthy or marginal.
- **Hop count** — how many nodes the packet traversed to reach the observer.
- **Packet timing** — when the observation arrived, used for ordering the packet history and aging topology edges.
- **Topology edges, labeled by evidence class** — which node was heard by which observer, on which path. The evidence that draws a line on the map, and how strong it is.
- **Infrastructure node records** — name, public key, device type, and the position the node advertises.
- **Companion ADVERT fields** — device type and GPS coordinates, in analytics rows for about 90 days.
- **Raw frames** — the whole frame of each packet, served on the public `/packets/{hash}/raw` route.
- **Other identifiers** — the 1-byte source and destination prefixes of direct messages, the display names of Public-channel senders, and the public keys carried by login requests.

No message text in the analytics rows: Waev decrypts Public-channel messages only to read the sender's display name and discards the text. The archived raw frames still carry each message's ciphertext, and anyone can decrypt Public-channel and guessable #hashtag messages from the archive, because the Public key is published and #hashtag keys derive from the channel name. Observers carry owner details: observer setup asks for an owner email, and a signed-in owner can claim an observer.

## What that retained data powers

The retained set powers a small set of surfaces.

**Live Map** draws topology edges labeled by evidence class. An edge appears when an enrolled observer records a packet path; it ages when observations stop arriving. The map shows what the network can prove about itself at a given moment, and labels what it infers.

**Network Stats** counts anonymous activity: unique nodes seen in the last hour, day, week. Companion signal records contribute to that count without identifying any device. The number tells you how busy the mesh is, not who's on it.

**Packet Search** gives you a queryable history of non-private observations: which nodes were active, over what time window, at what signal quality. Useful for after-action review and link-quality analysis.

**Outpost** surfaces per-node signal history — SNR over time, heard-by records — for the nodes that appear on the map.

The Live Map and Outpost need infrastructure nodes' names, keys, and advertised positions; Network Stats runs on signal metadata.

---

The choice about what not to collect is made at the architecture level, and it determines what's possible from that point forward. You can't breach data that was never stored. A field that a check blanks is only as safe as the code that runs the check. The [privacy-by-default framing](/blog/what-we-choose-not-to-know/) is the same one that governs [the never-captive stream](/blog/bring-your-own-broker/): the less the system knows, the more the operator controls.
